# MuScriptor 0.3.0の拍解析・発音時刻補正の比較

[English](MUSCRIPTOR_030_EVALUATION.en.md)

## 対象

2026-10-19に、従来のLibrosa方式（コミット`9d248cd7bd2cc06ecd270ca5b2faa91febae4d60`）と、MuScriptor 0.3.0およびロバスト回帰を使用するEarCopy Assist 0.1.5の拍解析を比較した。発音時刻補正は2026-10-18に、同一のMuScriptor medium採譜結果について補正前後を比較した。small、medium、largeの採譜モデル重みは更新前と同一である。

環境はWindows、Python 3.11.15、MuScriptor 0.3.0、Beat This! 1.1.0、PyTorch 2.2.2+cu121。拍解析はCPU、採譜はNVIDIA GeForce RTX 3060 Laptop GPU、float16を使用した。拍解析モデルはBeat This! final0、81,058,141 bytes、SHA-256は`8c328b45f59d8dd3dff219253ff6a8d6482be57d0133a29140e2febbf8eb8331`である。

## 拍解析

GTZAN miniの30秒音源100曲から、従来の評価設計と同じ各ジャンルのファイル名順で奇数番目の50曲を使用した。今回の条件調整には使用していない。GTZAN miniは`a61439e86c13037011fde8e0f0743ec55c50bce3`、Beat This! Annotations v1.1は`890407d158078527ab396b49fea3c8a83e5734ee`である。[Beat This!公式説明](https://github.com/CPJKU/beat_this#available-models)ではfinal0の学習対象からGTZANを除外している。

参照BPMは参照拍間隔の中央値から計算した。参照拍子を両方式へ同じ入力として与え、各方式のBPMと小節先頭位置からアプリが表示する等間隔の拍列・小節先頭列を生成した。時刻差70 ms以内で一対一対応し、曲ごとのF1を平均した。新方式が一定テンポを推定できない曲は、BPM正解数に含めず、拍と小節先頭のF1を0とした。

| 指標 | 従来方式 | EarCopy Assist 0.1.5 |
|---|---:|---:|
| テンポを出力した曲数 | 50 / 50 | 41 / 50 |
| BPM誤差4%以内 | 27 / 50（54%） | 37 / 50（74%） |
| 拍macro F1 | 0.7347 | 0.7437 |
| 小節先頭macro F1 | 0.3203 | 0.5517 |
| 50曲の処理時間 | 7.91秒 | 473.79秒 |

50曲中41曲でテンポを出力し、37曲がBPM誤差4%以内だった。残りの9曲も、BPMと拍子の手入力で採譜できる。再測定ではPyTorchのCPUスレッド数を2とし、同時にCUDA採譜とPyInstallerビルドを実行していた。処理時間はモデル読み込みを含む実測値であり、並行処理の条件が異なるため、方式間の速度比較には使用できない。

## アプリの処理を使った直接採譜・分離後採譜の比較

同じ5曲の60～80秒について、コミット`44a9e9ea643a1a27e3fac3adde42ae658b53e694`の`TranscriptionJobManager`で直接採譜と音源分離後採譜を実行した。MuScriptor medium、CUDA、float16、高精度、編成指定を使用した。編成は同じ`fixedInstruments`であり、アプリ既定の同族楽器候補追加と重複音符削除を有効にした。分離モデルはBS-RoFormer SW Fixedである。

音源分離後採譜では、アプリ既定のdrums成分追加、音高の誤検出削減、分離音源の音量によるベロシティ設定をすべてONにした。drums成分の追加率は20%であり、Bassへ追加するdrumsだけに350 Hz・4次Butterworthハイパスフィルターを適用した。原音の拍解析を使用し、分離音源単体の参照用採譜にも時刻補正を適用した。

各条件で補正ありの採譜を実行し、次に同じ分離音源と採譜イベントのキャッシュを使って、時刻補正だけを無効にした比較を実行した。モデルの再推論による差を含めず、補正後の音符選択とベロシティ設定を含むアプリの処理全体を比較した。全10条件の比較で、対応する音符ID、音高、推定楽器、出力トラック、音符数は同一だった。

MIDI音高と推定楽器が一致し、補正前の発音時刻差が120 ms以内の音符を一対一対応させ、補正前後で同じ音符IDを追跡した。F1は全1,427参照音符と各条件の全出力音符を対象とし、許容差ごとに対応を再計算した。

| 方式 | 同じ音符の対応数 | 補正なしの平均絶対誤差 | 補正ありの平均絶対誤差 | 減少率 |
|---|---:|---:|---:|---:|
| 直接採譜 | 539組 | 18.58 ms | 9.10 ms | 51.02% |
| 音源分離後採譜 | 543組 | 17.58 ms | 11.22 ms | 36.15% |

| 方式 | 20 ms許容F1・補正なし | 20 ms許容F1・補正あり | 50 ms許容F1・補正なし | 50 ms許容F1・補正あり |
|---|---:|---:|---:|---:|
| 直接採譜 | 0.2306 | 0.3393 | 0.3706 | 0.3720 |
| 音源分離後採譜 | 0.2774 | 0.3611 | 0.3868 | 0.3875 |

| 曲 | 直接採譜の平均絶対誤差・補正なし→あり | 音源分離後採譜の平均絶対誤差・補正なし→あり |
|---|---:|---:|
| Track00001 | 16.86 → 14.89 ms | 17.06 → 17.35 ms |
| Track00004 | 17.51 → 6.37 ms | 9.80 → 7.78 ms |
| Track00010 | 21.14 → 5.72 ms | 19.39 → 7.96 ms |
| Track00015 | 18.53 → 18.16 ms | 20.96 → 19.82 ms |
| Track00018 | 3.62 → 3.62 ms | 17.43 → 17.43 ms |

音源分離後採譜の主入力29件中6件で0 ms以外の補正を適用した。5曲中3曲で誤差が減少し、1曲で増加、1曲は補正量0 msだった。50 ms許容の一致数は527音符から528音符、出力音符数は1,298音符だった。今回の主な変化は、すでに検出されている音符の発音時刻誤差の減少である。

補正ありの全5区間の処理時間は、直接採譜91.65秒、音源分離後採譜239.93秒だった。直接採譜、音源分離後採譜の順に実行し、分離後採譜では解析用WAVと原音の拍解析結果を再利用した。分離音源と採譜イベントは各条件で新規計算した。補正量の計算と音符の時刻変更は合計6.75 msと13.84 msだった。処理時間は、この環境で各条件1回の実測値である。

この比較は、20秒区間・mediumモデル・指定編成における時刻補正の有無の比較である。直接採譜と分離後採譜では対応できた音符の集合が異なるため、平均絶対誤差の数値だけで分離の有無の優劣を判定できない。20秒区間での補正適用率は、曲全体を採譜した場合の適用率とは異なる可能性がある。

各曲・各入力の指標とモデル・音源・分離音源のSHA-256は、[アプリの処理を使った追加比較JSON](../benchmarks/data/muscriptor-030-application-onset-comparison.json)を参照する。

## 実装と条件

拍時刻はBeat This!の`Audio2Beats`へローカルのfinal0を明示して検出する。拍間隔をその中央値に対する整数の拍数へ変換して累積し、検出漏れと余分な検出を考慮した拍番号を求める。SciPyの`least_squares`でSoft-L1損失によるロバスト回帰を行う。8拍以上が必要であり、残差の絶対値の中央値が推定1拍長の5%以内の場合に採用する。拍子推定と発音時刻補正にはMuScriptorの処理を使用し、補正には検出した元の拍時刻を保持する。発音時刻補正は原音の拍解析を参照し、直接採譜と音源分離後採譜の各入力、参照用採譜の共通後処理後に適用する。補正量はMuScriptorの`with_onset_delay`で求める。異なる発音開始時刻40点以上、位相の集中度0.5以上、補正量の絶対値40 ms以内などの公式条件を使用する。音源先頭をまたぐ補正は、音符の長さを維持して開始時刻0秒を下限とする。

採譜キャッシュは補正前のイベントを保存し、再利用時も補正を1回適用する。保存する採譜入力別ノートは補正後の値であり、採譜オプションの再計算ではこの値を使用する。拍解析モデルはWindows本体の`resources/models/beat-this/final0.ckpt`へ同梱する。

## 記録と再現

拍解析の曲別指標と失敗した曲は[評価結果JSON](../benchmarks/data/gtzan-mini-tempo-downbeat.json)を参照する。

従来方式は上記基準コミットを選択した別作業ディレクトリで、同じ50曲と評価スクリプトを使用して測定する。新方式は次の順で実行する。

1. `uv run python scripts/download_beat_model.py`で拍解析モデルを取得・検証する。
2. `uv run python scripts/evaluate_tempo_downbeat.py --audio-root <GTZAN-mini>/genres --annotations-root <annotations>/gtzan/annotations/beats --split evaluation --output app/benchmark/new-tempo.json`で拍解析を測定する。
3. `scripts/prepare_babyslakh_benchmark.ps1`で正解MIDI付き音源を取得する。
4. `uv run python -m scripts.evaluate_application_onset_correction --dataset-root app/benchmark/public-data/babyslakh_16k --output app/benchmark/application-onset-comparison.json`でアプリの直接採譜・音源分離後採譜を比較する。`--work-dir`には新しい作業ディレクトリを指定すると、分離音源と採譜イベントを新規計算できる。
