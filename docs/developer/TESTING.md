# 全体テスト設計

[English](TESTING.en.md)

## 目的と適用範囲

EarCopy Assistの起動、入力、モデル管理、採譜、編集、再生、解析、保存、書き出し、設定、終了、配布を対象とする。
リリース可否は、利用者の操作と出力に対する証拠で判定する。
本書は2026-09-06のソース調査に基づく設計であり、ここに定義する追加試験の実装・実行状況は「追加」に区別する。
既存試験の存在、実行成功、製品全体の受入合格はそれぞれ別に記録する。

## 期待値の根拠

優先する回帰条件は`AGENTS.md`と[開発ガイド](DEVELOPMENT.md)、操作範囲は[利用ガイド](../USER_GUIDE.md)で確認する。
各ケースは根拠、入力、操作、期待結果、観測対象を持つ。期待結果は既知の音符・サンプル・ファイルを基準にする。

仕様不一致SPEC-01: `AGENTS.md`はSolo中のMuteを採譜結果モードのSolo対象採譜トラックに限定している。
開発ガイドと利用ガイドはSolo対象分離音源も、再生モードにかかわらずMute可能としている。
UC-17の該当期待値はこの不一致の解消待ちとする。操作可否の決定と日英文書・テストの一致が完了条件である。
他のケースは独立して実装・実行できる。SPEC-01が未解決の状態は全体受入未完了として記録する。

| F-03 | 30秒の原音と6分離音源。各分離音源に異なる周波数と共通のインパルス、既知の採譜ノートを用意 | 原音と各分離音源を個別識別。PCM入力の開始差は1 frame以内。ミックス期待値はfixture生成仕様から算出 |
| F-04 | 現行形式5のプロジェクト。音程・ドラム、同一音程重複、0.009／0.010／0.011秒、9.999／10.000／10.001秒、拍位相0.2秒、BPM 123.4、3/4・4/4・6/8 | 音符境界、時間軸、無効音符と直後リトリガー、ドラム10 ms補正・14 px以上の選択領域、保存項目 |

| F-07 | 権利処理済み30秒音源、small／medium／large、CPU／CUDA／Auto、実分離モデル | 音源・モデルSHA-256と環境を記録。推論ノート完全一致とは別に、健全性・既存ベンチマーク・工程完了を判定 |

試験用ディレクトリとUserDataはケースごとに分離する。入力ファイルは検証前後でSHA-256を照合する。
出力は同じ書き出し関数による期待値生成ではなく、MIDIはmido、MusicXMLはXML解析とOSMD、WAVはsoundfileで再読込する。
保存往復は時刻など明示した可変メタデータ以外の全フィールドを比較する。配列の並び順に意味がある項目は順序も比較する。
音声の数値照合は出力ノードで取得したPCMを使用する。物理デバイスへの音の出力は別の受入項目とする。
PCMの10 msゲイン変化と開始待機区間を除いて選択信号を照合し、SoundFont側は左右チャンネル・発音数・スケジューリング時刻を確認する。

## 状態遷移・組合せ・障害注入

ケースごとに成功経路だけでなく、次の遷移をパラメーター化する。

| 対象 | 必須遷移・組合せ | 観測 |
|---|---|---|
| プロジェクト | 未作成→作成→編集中→保存済み→再編集→終了→再読込。保存中の編集・切替・終了 | projectId、未保存状態、保存内容、Undo対象 |
| ジョブ | 待機→準備→分離→採譜→後処理→完了。各工程から取消・失敗→次ジョブ | jobId、sequence、最後の設定、部分結果 |
| 再生 | 停止→準備→再生→一時停止→再開。準備中の取消・シーク・再選択、終端→反復 | 再生意図、実イベント、開始frame、発音、残存タイマー |
| 保存・解析 | 要求A→要求B→B応答→A応答、およびA失敗。別プロジェクトを挟む | 最新の対象・設定と応答の対応 |
| 必須全組合せ | 3再生モード×2再生状態×分離あり／なし。モード全9遷移。F-01の8組 | 実行した組と未実行の組を列挙 |
| 実モデル | small／medium／largeをCPUで直接・分離後採譜。CUDA対応環境で3モデルを両モード、AutoをCUDAあり／なしで実行 | 高精度は全組。高速はCPU／CUDAと3モデルを追加。未配置・資源不足は未実行として記録 |
| その他設定 | 拍子、ズーム、言語、量子化分解能、入力形式の各値と全2因子組合せ | 生成した組合せ表を証拠に添付。既知の3因子以上の回帰条件は明示ケースで追加 |

非同期試験は応答を保留・解放して順序を制御する。0／100／1,000 msの遅延と、利用可能なPCM残量を超える供給遅延を使う。
長さ0、最終frame、チャンク境界の前後1 frame、ノート境界、リピート境界を明示的に通す。
通常成功ケースは未処理例外・予期しない停止0件、故障ケースは期待したエラーだけが表示され、再操作完了が必須となる。
待機はイベント・画面状態・ファイル出力の成立で終了し、タイムアウトには待っていた条件を記録する。
待機時間の上限はケース・モデル・環境ごとに試験実装で定義し、計測値と区別する。

各層の結果を分けて示す。単体の成功件数をE2Eや実モデル受入の成功件数へ加算しない。
再実行で成功した不安定試験は、最初の失敗・発生条件・修正と再検証が追跡できる状態で判定する。
必須ケースの証拠が不足した候補は受入未完了とする。CUDA・実デバイスなど専用環境が必要なケースは対象環境で完了する。
ソース変更後は影響ケースと共通回帰を再実行する。配布物再生成後は新しいSHA-256に対して配布受入を実行する。
コードカバレッジは未通過分岐の発見に使い、操作・遷移・出力の受入証拠と併記する。

現行ワークフローはこのケース別判定と証拠保存を自動化していない。実装完了までは公開責任者がケース表を照合する。
本書でCIの自動判定が実装済みとは扱わない。配布ビルドの実行時期はリポジトリの運用条件に従う。

## 実装順序と完了条件

1. 期待値とデータを用意する。SPEC-01を解消し、F-01〜07の生成方法・参照値・SHA-256、36ケースと組合せ表を登録する。
2. 実サービスとTypeScriptクライアントの結合を追加する。音声準備、PCM、SSE、保存・再読込、各書き出しを実ファイルまで照合する。
3. UC-24の1プロジェクト全工程を実Electronで実装する。次に全P0ケースを追加し、逆順応答・取消・失敗後再操作を含める。
4. P1ケースと実Canvas・出力デバイス・継続利用を追加する。画面、状態、音声、成果物の照合を完成させる。
5. 実モデルと配布候補で同じケースを実行し、ケース別の結果・ログ・成果物をCIまたは受入記録に保存する。

各段階はテストを実行可能にした時点で完了する。設計書、空の試験、模擬実装だけの試験を後続層の実装完了として扱わない。
担当は、変更実装者が回帰ケースと結合試験、検証担当者が実行証拠、公開責任者が候補と受入結果の対応を確認する。
同一人物が兼任する場合も、実装・実行・公開判定の記録は区別する。
